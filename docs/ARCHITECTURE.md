# Architecture

One Node process serves the Astro standalone build. SQLite is opened with WAL, foreign keys, a busy timeout and explicit forward migrations. `bin/migrate.ts` takes an online SQLite backup before a schema change. All paths come from environment variables. `bin/server.mjs` filters forwarding headers using the TCP socket peer before delegating to Astro's official standalone handler. Host allowlisting is independent of IP trust. Do not run the generated entrypoint directly in production.

`src/lib/content.ts` is the publication boundary used by public pages, RSS, API and MCP. Published means `status=published` and an effective UTC publication timestamp. Opaque keyset cursors order by timestamp plus ID. FTS queries are parameterized and user terms quoted. The editorial service snapshots old revisions transactionally and retains old slugs as redirects. Revision restoration always makes a draft. Tags are stored as JSON, indexed through SQLite JSON queries; FTS5 indexes text. Projects are independently public once saved.

One administrator uses Argon2id and mandatory RFC 6238 TOTP. Successful TOTP counters are consumed atomically. Session handles are random and HMAC hashed at rest; CSRF tokens are bound to a session and exact configured Origin. SQLite persists login limits and the shared API/MCP budget across restarts. The configured session/CSRF secrets must be stable and private. Rotating the session secret invalidates existing sessions. Enrollment/recovery revokes every session. TOTP secrets are stored in the private database; setup secret and URI are displayed only in the interactive terminal. No authentication bodies are logged.

Markdown goes through a strict HTML sanitizer. Sharp decodes uploads with a pixel limit and accepts only JPEG/PNG/WebP, then rotates and re-encodes to WebP without metadata. Names are random UUIDs. Uploads are public immutable assets; do not upload confidential images even when a draft uses them. Raw archives are never served. Original X source records are separate from editable draft text and deduplicated by source ID. Conversion of a selection and linking its source IDs is atomic; a repeated import never updates an existing editorial draft.

Analytics credentials stay on the server. The Umami API client permits only the internal service name or loopback, uses timeouts, caches for 15 minutes and keeps the last successful SQLite snapshot. Public top pages are intersected with currently published slugs, so a withdrawn post cannot leak through historical analytics. Tracking is excluded from the admin, local webdriver tests and `?tracking=off`. Named events cover project links, marked profile links and searches with no results. No custom visitor identity, recordings or social metrics are used. Replays are not configured.

The blog and Umami are separate Compose projects sharing only a named analytics network. PostgreSQL remains on Umami's private network. Caddy runs on the host; only loopback ports are published. The blog application owns blog security headers; Caddy does not duplicate them. Runtime container root is read-only, capabilities dropped, UID/GID 1000, with explicit writable bind mounts. PostgreSQL UID/GID is 999. Umami's upstream image runs as 1001.

Backups use SQLite's online backup API and PostgreSQL's custom-format `pg_dump`; open storage files are never copied. Media is additive with no destructive deletion UI, so the snapshot copy retains references present at SQLite backup time. Deployments stop the sole writer before copying and migrating. Rollback restores the previous SQLite snapshot and image; later uploads remain on disk. Forward migrations must remain compatible with the previous executable or require snapshot rollback. A manual rollback preserves a fresh backup of current content first. Release snapshots are pinned against normal seven-day rotation until superseded.
